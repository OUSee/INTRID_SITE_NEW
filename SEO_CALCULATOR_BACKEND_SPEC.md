## 1. Задача

Нужно подключить серверную часть к уже готовому frontend SEO-калькулятора.

Frontend уже реализует:

1. ввод URL или сценарий «Сайта нет / в разработке»;
2. опциональный запуск существующего экспресс-аудита в новой вкладке;
3. получение предварительно заполненных параметров сайта;
4. редактирование параметров пользователем;
5. расчет стоимости и сроков;
6. пересчет результата в реальном времени после изменения параметров;
7. форму заявки после расчета.

На backend требуется реализовать:

- анализ сайта для предварительного заполнения параметров;
- серверную валидацию всех данных;
- серверный повторный расчет стоимости и сроков;
- прием и обработку заявки;
- проверку CAPTCHA в соответствии с существующей инфраструктурой проекта;
- защиту внешних запросов к пользовательскому домену;
- кэширование и ограничение частоты тяжелых операций.

### Важный момент

**Frontend не вызывает backend при каждом изменении цены.**  
После первого анализа расчет на 2-м и 3-м шагах выполняется локально в `app.js`.

Backend вызывается только:

- при первоначальном анализе сайта;
- при отправке итоговой заявки.

Поэтому сервер должен иметь собственную копию формулы расчета и повторно рассчитывать результат во время приема заявки.

# 2. Пользовательский сценарий

## Шаг 1 — URL

Пользователь может:

- ввести URL сайта;
- выбрать «Сайта нет / в разработке», если URL пустой;
- при наличии URL выбрать «Экспресс-аудит»;
- выбрать дополнительные услуги:
  - улучшение репутации;
  - продвижение в нейросетях.

### Взаимодействие URL и «Сайта нет»

Текущий frontend работает так:

- URL пустой → чекбокс «Сайта нет / в разработке» доступен;
- в URL введено любое значение → чекбокс автоматически снимается и становится `disabled`;
- URL снова полностью очищен → чекбокс снова доступен;
- если «Сайта нет» уже выбран, поле URL все равно остается активным;
- начало ввода URL автоматически снимает «Сайта нет».

Backend все равно обязан самостоятельно проверять согласованность `site` и `site_missing`.

Нормальный запрос не должен содержать одновременно:

```json
{
  "site": "https://example.ru",
  "site_missing": true
}
```

Такую комбинацию рекомендуется считать ошибочной.

---

## Экспресс-аудит

Чекбокс «Экспресс-аудит» **не требует нового API SEO-калькулятора**.

При нажатии кнопки анализа frontend самостоятельно открывает новую вкладку:

```text
GET /submit/express-seo-audit?site=https%3A%2F%2Fexample.ru&audit_origin=external
```

и параллельно запускает обычный запрос SEO-калькулятора.

Frontend также вызывает существующий:

```js
expressAuditFlow.rememberSource(site)
```

### Следствие для backend

Новый endpoint `/submit/seo-calculator-analyze` не получает и не должен обрабатывать поле `express_audit`.

Необходимо лишь сохранить работоспособность существующего:

```php
actionExpressSeoAudit()
```

### Важная оптимизация

Если пользователь выбрал экспресс-аудит, в один момент могут стартовать две операции по одному домену:

1. анализ для SEO-калькулятора;
2. анализ для экспресс-аудита.

Поэтому желательно использовать **общий слой анализа и общий кэш** для обоих сценариев, чтобы не делать параллельно два RDAP/WHOIS-запроса и два одинаковых запроса к сайту.

В проекте уже используются ключи вида:

```text
analiz:rdap:{domain}
analiz:page:{domain}
```

и их желательно переиспользовать.

Для предотвращения cache stampede желательно предусмотреть lock/mutex на домен во время первичного заполнения кэша.

# 3. Новые backend routes

Предлагаемые Yii2 actions:

```php
public function actionSeoCalculatorAnalyze()
public function actionSeoCalculatorRequest()
```

Они автоматически соответствуют маршрутам:

```text
POST /submit/seo-calculator-analyze
POST /submit/seo-calculator-request
```

Не рекомендуется перегружать существующий универсальный `actionCalc()`.

Существующий `actionSeo()` тоже нельзя просто подключить без адаптации:

- он ожидает обычный POST;
- формат ответа отличается от текущего frontend-контракта;
- в нем другая логика CAPTCHA/отправки;
- SEO-калькулятор передает вложенный объект `calculation`.

При этом из существующих actions можно переиспользовать отправку писем через `enqueueEmail()` и инфраструктуру шаблонов.

# 4. Формат запросов

Frontend отправляет JSON:

```http
Content-Type: application/json
Accept: application/json
X-Requested-With: XMLHttpRequest
```

Если на Yii-странице присутствуют CSRF meta-теги, frontend также передает:

- CSRF-параметр в JSON body;
- `X-CSRF-Token` в header.

## Yii2 JSON parser

Нужно убедиться, что Yii умеет разбирать `application/json`.

Предпочтительный вариант — штатный parser:

```php
'request' => [
    'parsers' => [
        'application/json' => 'yii\web\JsonParser',
    ],
],
```

После этого использовать:

```php
$post = Yii::$app->request->bodyParams;
```

или:

```php
$post = Yii::$app->request->getBodyParams();
```

Если глобальный parser подключать нельзя, конкретный action может разобрать:

```php
json_decode(Yii::$app->request->getRawBody(), true)
```

но предпочтительнее единый штатный механизм.

### CSRF

**Не отключать CSRF для новых endpoints.**

В `SubmitController.php` уже есть пример `actionGetSeoData()`, где CSRF отключается. Для SEO-калькулятора это поведение копировать не нужно.

# 8. Что должен реально определять анализатор

Здесь важно отделить **обязательный API-контракт** от **качества автоматического определения**.

Frontend требует все поля, но не все параметры можно надежно вывести из HTML сайта без дополнительных источников.

## Надежно или относительно надежно можно определить

- возраст домена через RDAP/WHOIS;
- примерное количество страниц через sitemap;
- примерное количество разделов через структуру sitemap/URL;
- тип сайта по структуре и признакам;
- доступность самого сайта.

## Нельзя надежно определить только по сайту

- факт SEO-продвижения в прошлом;
- реальную конкуренцию ниши;
- фактическую географию будущего продвижения;
- размер согласованного семантического ядра.

Для таких полей допустимо возвращать начальные значения, которые затем пользователь исправит вручную.

# 10. Защита анализа URL

Frontend уже валидирует URL, но backend обязан повторить проверки.

Минимальные требования:

- только `http` / `https`;
- запрет credentials в URL;
- запрет нестандартных портов;
- запрет IP-literal вместо домена;
- корректный hostname;
- нормализация IDN/punycode при необходимости;
- ограничение длины входного URL;
- запросы только к анализируемому публичному домену.

## SSRF

Особенно важно защитить любой server-side fetch.

Нельзя полагаться только на строковую проверку домена.

Перед HTTP-запросом необходимо:

1. разрешить DNS;
2. проверить все полученные IPv4/IPv6;
3. запретить loopback, link-local, private, multicast, reserved и внутренние диапазоны;
4. повторять проверку после каждого redirect;
5. ограничить число redirects;
6. ограничить timeout и максимальный размер response;
7. не разрешать переход на другой небезопасный host;
8. учитывать DNS rebinding.

То же относится к sitemap.

# 11. Sitemap / количество страниц

Рекомендуемый порядок:

1. проверить sitemap из `robots.txt`;
2. проверить `/sitemap.xml`;
3. поддержать sitemap index;
4. учитывать только внутренние URL того же сайта;
5. дедуплицировать URL.

Необходимо установить серверные лимиты на:

- глубину sitemap index;
- число sitemap-файлов;
- число URL;
- размер ответа;
- время запроса.

Для тарифа достаточно различать:

```text
1
2–10
11–50
51–200
201–1000
1001+
```

Если получение точного числа слишком дорого, сервер может остановить подсчет после подтверждения категории `1001+`. Но если точное количество уже известно, лучше вернуть его в `pages`, так как пользователь видит точное значение в input.

# 12. Количество разделов

Текущий frontend использует визуальные категории:

```text
1–5
6–9
10–20
21–50
51–100
101+
```

При этом **ценовая логика** объединяет `21–50` и `51–100`.

Для цены:

| Разделы | Надбавка |
|---:|---:|
| 1–5 | +0 ₽ |
| 6–9 | +1 000 ₽ |
| 10–20 | +2 000 ₽ |
| 21–100 | +3 000 ₽ |
| 101+ | +6 000 ₽ |

Для сроков действуют другие границы:

| Разделы | Поправка к первым результатам | Поправка к ТОП-10 |
|---:|---:|---:|
| <= 100 | +0 | +0 |
| 101–1000 | +1 мес. | +1 мес. |
| > 1000 | +1 мес. | +2 мес. |

То есть переход **100 → 101** должен менять и стоимость, и сроки.

# 14. Диапазон цены

Сначала рассчитывается:

```text
base = 12 000 + все основные надбавки
```

Затем:

```text
min = base × 85%
max = base × 115%
```

Обе границы округляются до сотен по логике Excel `ROUND(..., -2)`.

В PHP лучше явно использовать:

```php
$min = round($base * 0.85, -2, PHP_ROUND_HALF_UP);
$max = round($base * 1.15, -2, PHP_ROUND_HALF_UP);
```

На frontend для устранения погрешностей floating point используется целочисленная эквивалентная формула.

# 15. Дополнительные услуги

Дополнительные услуги выбираются только на первом шаге, но сохраняются в параметрах расчета.

```json
"services": {
  "reputation": true,
  "geo": false
}
```

Стоимость:

| Услуга | Прибавка |
|---|---:|
| `reputation` | +2 000 ₽/мес. |
| `geo` | +6 000 ₽/мес. |

### Порядок расчета

Дополнительные услуги прибавляются **после** округления SEO-диапазона:

```text
totalMin = roundedSeoMin + extras
totalMax = roundedSeoMax + extras
```

Не нужно еще раз применять 85%/115% к дополнительным услугам.

# 16. Расчет сроков

## Возраст

### `0–5` месяцев

```text
первые результаты: 2–4 мес.
ТОП-10: 7–10 мес.
```

### `6–11` месяцев

```text
первые результаты: 2–4 мес.
ТОП-10: 6–9 мес.
```

### `12–36` месяцев включительно

```text
первые результаты: 2–3 мес.
ТОП-10: 5–8 мес.
```

### Более 36 месяцев

```text
первые результаты: 2–3 мес.
ТОП-10: 4–7 мес.
```

### Неизвестный возраст

Используется расчетная категория:

```text
1–3 года
```

но в UI возраст остается:

```text
Не определён
```

---

## Поправка по количеству разделов

```text
<= 100      => [0, 0]
101–1000    => [+1, +1]
> 1000      => [+1, +2]
```

Первое число применяется к «первым результатам», второе — к ТОП-10.

---

## Поправка по конкуренции

```text
low     => [-1, -1]
medium  => [0, 0]
high    => [+1, +2]
```

Финальное значение каждого срока:

```text
max(1, базовый срок + поправка разделов + поправка конкуренции)
```

# 17. Пример серверной функции расчета

Упрощенный каркас:

```php
final class SeoCalculatorPricingService
{
    public function calculate(array $p): array
    {
        // 1. validate enums
        // 2. validate positive integers
        // 3. derive age category from age_months
        // 4. calculate additions
        // 5. calculate base
        // 6. calculate 85/115 range with HALF_UP rounding
        // 7. add optional services
        // 8. calculate timing corrections

        return [
            'version' => 'excel-2026-09-09-pm-1',
            'base' => $base,
            'additions' => $additions,
            'seo' => [$seoMin, $seoMax],
            'services' => $selectedServices,
            'total' => [$totalMin, $totalMax],
            'first' => [$firstMin, $firstMax],
            'top10' => [$top10Min, $top10Max],
        ];
    }
}
```

`age_category`, пришедшему из браузера, доверять не нужно. Его следует вывести из `age_months` на сервере.

# 20. Поле `service` и `parameters.services` — разные сущности

Не путать два поля.

## `service`

Это выбранная коммерческая модель SEO в форме заявки.

В текущей разметке два значения:

```text
СЕО по предоплате с гарантией результата
Оплата за ключевые фразы в ТОП10
```

Backend должен использовать allowlist, а не принимать произвольную строку.

---

## `calculation.parameters.services`

Это дополнительные услуги, влияющие на рассчитанную месячную стоимость:

```json
{
  "reputation": true,
  "geo": false
}
```

# 21. Валидация заявки

## Обязательно

```text
tel
service
calculation.parameters
```

Также проверить весь набор параметров расчета.

## Телефон

Frontend считает корректным номер, который после удаления нецифровых символов:

- содержит 11 цифр;
- начинается с `7` или `8`.

Backend должен повторить проверку.

## Email

Поле необязательное.

Если заполнено — валидировать как email.

## Имя

Поле необязательное.

Ограничить длину и очистить от управляющих символов.

## `form_page`

Не доверять как источнику безопасности.

Это только служебная информация для заявки/аналитики.

# 22. Сервер не должен доверять `calculation.result`

Главное правило endpoint заявки:

```text
calculation.result — только снимок того, что видел пользователь.
```

Нужно взять:

```json
calculation.parameters
```

повторно их валидировать и вызвать серверный:

```php
SeoCalculatorPricingService::calculate(...)
```

В письмо, CRM и логи должна уходить **серверная сумма**.

Дополнительно полезно сравнить:

```text
client result
server result
```

и логировать несовпадения.

Нельзя принимать цену из браузера как окончательную.

# 24. Ошибки API

Рекомендуемый единый формат:

```json
{
  "success": false,
  "error": "Текст понятной пользователю ошибки"
}
```

Frontend также понимает поле:

```json
{
  "success": false,
  "message": "..."
}
```

но лучше придерживаться одного формата.

Рекомендуемые HTTP-коды:

| Код | Ситуация |
|---:|---|
| 400 | некорректный input |
| 403 | CSRF / CAPTCHA |
| 422 | данные формально валидны, но анализ невозможен |
| 429 | rate limit |
| 502/503 | временно недоступен внешний источник |
| 500 | внутренняя ошибка |

Не возвращать HTML error page для AJAX endpoint.

# 25. CAPTCHA

В `SubmitController.php` уже есть:

```php
reGoogle()
extractCaptchaToken()
```

которые работают с Яндекс SmartCaptcha:

```text
https://smartcaptcha.yandexcloud.net/validate
```

и параметром:

```php
Yii::$app->params['smartcaptchaServerKey']
```

Новый endpoint заявки должен переиспользовать существующую серверную проверку.

Frontend передает токен под именем:

```text
g-recaptcha-response
```

`extractCaptchaToken()` уже поддерживает это поле.

### Текущий frontend

В mock-режиме CAPTCHA не запускается.

В live-режиме `app.js` пока содержит собственную заготовку вызова `window.smartCaptcha`.

Так как на серверной версии проекта SmartCaptcha уже интегрирована, frontend-команда может позднее заменить этот кусок на общий существующий механизм проекта.

Для backend-контракта важно только одно:

> если CAPTCHA обязательна для production-заявки, endpoint обязан валидировать полученный token на сервере.

# 27. Кэширование


- по IP;
- по домену;
- отдельно на тяжелый analyze endpoint.

# 30. Особенности существующего backend

## `actionGetSeoData()`

Можно использовать его внутренние идеи и helpers, но не нужно копировать:

```php
$this->enableCsrfValidation = false;
```

Новые endpoints должны оставаться с CSRF.

## `actionSeo()`

Можно переиспользовать email-инфраструктуру, но текущий формат ответа:

```json
{
  "status": true,
  "data": "..."
}
```

**не подходит** текущему `requestJson()` SEO-калькулятора.

Калькулятор требует:

```json
{
  "success": true,
  "data": {}
}
```

## `actionExpressSeoAudit()`

Существующий route остается самостоятельным.

SEO-калькулятор только открывает его в новой вкладке и не ждет его результата.

В текущем action после раннего:

```php
return $this->render(...)
```

остается старый недостижимый код синхронного анализа. Его можно позднее почистить отдельно, но это не блокирует интеграцию SEO-калькулятора.

# 33. Definition of Done

Backend можно считать готовым, когда:

- [ ] `/submit/seo-calculator-analyze` работает с JSON и CSRF;
- [ ] `/submit/seo-calculator-request` работает с JSON и CSRF;
- [ ] response format полностью соответствует frontend;
- [ ] возраст домена берется из RDAP/WHOIS или возвращается `null`;
- [ ] `site_missing=true` не запускает внешний анализ;
- [ ] параметры всегда проходят серверную enum/int-валидацию;
- [ ] стоимость пересчитывается сервером;
- [ ] сроки пересчитываются сервером;
- [ ] граница разделов `100 → 101` меняет цену и сроки;
- [ ] дополнительные услуги прибавляются после округления;
- [ ] клиентская сумма не считается доверенной;
- [ ] CAPTCHA проверяется сервером;
- [ ] заявка отправляется через существующую очередь;
- [ ] analyze защищен от SSRF;
- [ ] есть timeouts, лимиты и rate limiting;
- [ ] RDAP/site-data используют кэш;
- [ ] параллельный экспресс-аудит не создает двойную тяжелую работу;
- [ ] staging протестирован на контрольных кейсах;
- [ ] после этого frontend переключен с `mock` на `live`.

# 34. Коротко: минимальный порядок реализации

1. Создать `SeoCalculatorPricingService` и покрыть контрольными тестами.
2. Создать `actionSeoCalculatorAnalyze()`.
3. Переиспользовать RDAP/WHOIS и существующий cache.
4. Добавить безопасный анализ sitemap/структуры сайта.
5. Создать `actionSeoCalculatorRequest()`.
6. На request пересчитывать результат через `SeoCalculatorPricingService`.
7. Подключить SmartCaptcha server validation.
8. Подключить `enqueueEmail()` и отдельный email template.
9. Протестировать API отдельно.
10. Переключить frontend на `data-seo-calculator-mode="live"`.
11. Провести end-to-end тест `/seo` и `/promotion`.
